# Operations, trust boundaries and limits

## Runtime identities

The backend verifies Supabase signatures/issuer/audience/time and maps `sub` to an application profile. JWT role claims and request acting-user/membership fields do not authorize team actions. Legacy HS256 tokens are checked by the same project's Auth `/user` endpoint and then the API's expected claims. Asymmetric tokens use the project's JWKS. Offline asymmetric JWT verification cannot instantly revoke an already valid token after global sign-out; current database membership removal is immediate for team operations. Account disable/token denylisting is production work.

`app_api` and `app_worker` are non-owner, non-BYPASSRLS roles with no direct application DML. Narrow SECURITY DEFINER commands own mutations; separate policy-reader helpers prevent recursive RLS. The API database connection and its verified server context are trusted: a stolen API credential can forge context and call its commands. PostgreSQL GUCs are not end-user authentication. Never expose runtime credentials or SQL access to browsers. Worker/server Storage keys are privileged trusted credentials. The migrator is a separate setup capability.

Every content operation resolves an active membership. Removed memberships never reactivate; rejoin allocates a new identity, leaving old grants/conversations behind. Last-admin changes serialize through a team gate. Admin can issue explicit blind ACL commands but cannot list hidden documents, inspect their reader metadata, read them implicitly, or inspect another membership's chat.

## Upload and processing lifecycle

Accepted files: valid nonempty UTF-8 TXT and text-bearing PDF, maximum 20 MiB. PDF magic is checked before storage; parsing happens in a dedicated child process with a 256 MiB JS heap cap, 60-second deadline and 200-page/500,000-character/500-chunk bounds. Service secrets are omitted from the child environment. PDFs with any page containing fewer than ten extracted text characters are rejected. Encrypted, malformed, scanned/image-only PDFs have no OCR fallback. This contains parser-process failures but is not a sandbox, native-memory cap, antivirus or content-disarm service.

The initial Windows thread-based parser produced intermittent host-process exits during verification. An [upstream PDF.js issue](https://github.com/mozilla/pdf.js/issues/21934) also reports this pattern and identifies `worker_threads` usage as unsupported. That report is supporting context, not proof of the precise fault on this laptop. The application now uses a separate process so a parser failure cannot directly terminate its parent; cleanup completes before returning text, and the parent enforces termination/deadline.

Allocate a durable storage intent before the private PUT. Finalize under the team gate, rechecking role/access and intent lease. Failed finalization leaves a cleanup path. Expired unreferenced intents are reconciled; a purged intent is swept again after an hour to remove delayed writes. Original object names are random; uploads never overwrite an existing object. Service-side credentials could still modify objects out of band; operators must not use them for arbitrary writes.

Versions/chunks are immutable after readiness. All chunks must finish before activation. Highest successfully ready revision wins; failure or late older completion cannot replace a newer ready revision. One active embedding profile is supported across current documents; profile changes require a planned reindex. Search uses exact cosine ordering over a materialized, authorized current-ready set, with eight context chunks. No approximate vector index or relevance threshold is currently used. This favors transparent authorization over large-corpus throughput and may return weak evidence; the model's no-citation result becomes a fixed insufficient-sources response.

BullMQ/Redis is delivery transport; PostgreSQL jobs, leases/fences and outbox are durable intent. The relay republishes eligible unfinished jobs even after publication acknowledgement. Redis should use noeviction and persistent storage. Worker concurrency is one in this laptop configuration. Claim leases last 15 minutes and heartbeat every 30 seconds; quota attempts last two minutes and heartbeat every 30 seconds. Failed processing/cleanup is capped at three claims with exponential backoff. Terminal failures require operator review, followed by an intentional fenced requeue; there is no public reset endpoint. Do not mutate immutable ready chunks or blindly reset all jobs.

Deletion first tombstones the document, removes current selection, permanently invalidates affected assistant answers and cancels processing fences. Retriable purge then removes originals/chunks and clears chunk pointers only on invalidated provenance. Identifiers/audit/usage tombstones remain for integrity. A late worker cannot restore deleted content.

## Answer delivery and quotas

No streaming. Resolve identity and membership, reserve one quota hold, retrieve current-readable chunks, recheck before dispatch, invoke the provider, reject invented labels, then recheck every supplied chunk and current version under the same team gate used by revocation/delete. Save answer + every potential source + quota settlement in one transaction. All prior generated answers are omitted from subsequent factual context. Documents are encoded as data; the model receives no tool capability. These controls constrain access and citations, not semantic truth or universal prompt-injection resistance.

If revocation/delete commits first, finalization fails and releases the hold. If finalization acquires the gate first, revocation waits. A packet authorized before a later revocation cannot be recalled after commit, during HTTP delivery, from a browser cache already rendered, screenshots or external provider logs. Later history/citation/feedback/replay rechecks permissions and hides the entire assistant answer if any cited or uncited potential source is inaccessible. Temporary grant loss may permit reappearance after a new explicit grant; document deletion is permanently invalidating. Old retained versions remain inspectable as historical citations only with current document access.

The default monthly budget is 1,000 **successfully saved grounded answers** per team, by PostgreSQL UTC calendar month. Insufficient-source results and failed/blocked attempts release their holds. Completed idempotent replay does not regenerate or charge. An attempt settles the period recorded when reserved, even across a month boundary. Lowering a limit blocks new holds but honors existing valid holds. Application quotas are not provider spend caps: provider calls can cost money even if final authorization rejects delivery.

## UI and application hardening

The frontend uses real bearer API requests and plain React text rendering. Public environment settings contain only a public Supabase URL/key and API URL. Private credentials never use `NEXT_PUBLIC_`. CORS accepts the configured exact frontend origin and exposes only the attachment filename/request-ID headers needed by the client; responses are no-store. An in-memory IP limiter bounds requests per minute, not distributed account abuse. Local startup binds API to loopback. Supabase browser session storage has the normal XSS exposure of browser-readable tokens; add a reviewed CSP and hardened session architecture before Internet exposure. A shared client per runtime avoids duplicate Auth-client creation under React Strict Mode.

On team change/logout, protected panels clear; server refresh on focus/every 15 seconds updates permissions/history, and errors clear protected content. This is a bounded refresh interval, not instant erasure of content already displayed. Citation dialogs clear on refresh. The API, not the UI, decides permission. Lists use bounded pages for documents/audit; conversation/message history and membership rosters are not yet paginated. UI list navigation is intentionally minimal.

## Retention and production improvements

There is no automatic age-based deletion of conversations, audit, provenance, usage or source versions. Deleting one's own conversation removes private text/sources/feedback while retaining opaque request/quota tombstones. Deleting a document removes originals/chunks through jobs and keeps integrity tombstones. Audit is append-only to runtime users; retention/export is a separate privileged, reviewed operational process, not an implemented public API. Default retention and regulatory obligations need product/legal review; no compliance claim is made.

Before deployment: private network/TLS and least-privilege secret rotation; hardened verified ingress and distributed rate limits; account-disable strategy; independent threat review; malware scanning/process isolation; provider data-processing/retention settings; validated model grounding/injection evaluations; retention tooling; deterministic UTC-boundary tests; fault-injected real Redis/Storage recovery; accessible keyboard/dialog review; database backups/restore drills and monitoring/alerts; audited reindex and terminal-job retry tooling; pagination, vector scale/performance measurements; pinned container digests and repeat vulnerability reviews. No production availability, scalability or regulatory certification is claimed.
